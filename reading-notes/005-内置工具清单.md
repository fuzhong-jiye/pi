# 005 - 内置工具清单

## 概述

pi 有 **7 个内置工具**，定义在 `packages/coding-agent/src/core/tools/`：

| 工具名 | 文件 | 类型 | 用途 |
|--------|------|------|------|
| **read** | `read.ts` | 只读 | 读取文件内容（文本）+ 图片识别 |
| **bash** | `bash.ts` | 执行 | 执行 shell 命令 |
| **edit** | `edit.ts` | 写入 | 精确文本替换（多编辑一次提交） |
| **write** | `write.ts` | 写入 | 创建或覆盖文件 |
| **grep** | `grep.ts` | 只读 | 基于 `rg` 的内容搜索 |
| **find** | `find.ts` | 只读 | 基于 `fd` 的文件名搜索（glob） |
| **ls** | `ls.ts` | 只读 | 列目录 |

## 工具分组

[`index.ts`](packages/coding-agent/src/core/tools/index.ts) 预设了三种工具组合：

```typescript
// 编码模式（4 个）：用于创建/修改代码
createCodingToolDefinitions()  → [read, bash, edit, write]

// 只读模式（4 个）：用于探索/分析代码
createReadOnlyToolDefinitions() → [read, grep, find, ls]

// 全部（7 个）
createAllToolDefinitions()     → [read, bash, edit, write, grep, find, ls]
```

## 各工具详细

### read — 读文件 + 图片

参数 schema（`read.ts:21-23`）：

```typescript
{
  path: string,       // 文件路径
  offset?: number,     // 起始行（1-indexed）
  limit?: number,      // 最大行数
}
```

- 自动检测图片类型（jpg/png/gif/webp），以 base64 返回
- 大文件自动截断（默认 50KB 或 2000 行）
- 支持可插拔 `ReadOperations`（见下文"可插拔执行层"）

### bash — 执行命令

参数 schema（`bash.ts:24-25`）：

```typescript
{
  command: string,     // shell 命令
  timeout?: number,    // 超时秒数
}
```

执行流程：

```
LLM 生成 bash 调用 → 参数校验 → BashOperations.exec() → OutputAccumulator 累积输出 → 截断/持久化 → 返回给 LLM
                              ↑
                     这是可替换的注入点
```

- 输出超 50KB/2000 行会自动截断，完整内容写入临时文件
- 支持超时控制（`setTimeout` + `killProcessTree(pid)` 杀死整个进程树）
- 支持 `AbortSignal` 取消
- 子进程 PID 注册到全局 `trackedDetachedChildPids`，会话退出时统一清理
- Shell 解析优先级：用户指定 > Git Bash（Windows）> `/bin/bash`（Unix）> `sh`
- 支持可插拔 `BashOperations`（见下文"可插拔执行层"）

bash 工具有**两套执行路径**：

| 路径 | 入口 | 用途 |
|------|------|------|
| 工具调用路径 | `createBashToolDefinition().execute()` | 模型通过工具调用执行 bash |
| 编程调用路径 | `executeBashWithOperations()`（`bash-executor.ts`） | `AgentSession.executeBash()`、RPC 模式等 |

两套路径共享同一个 `BashOperations` 接口，各自独立处理输出截断、ANSI 清洗、二进制过滤。

### edit — 精确文本替换

参数 schema（`edit.ts:35-52`）：

```typescript
{
  path: string,        // 目标文件
  edits: Array<{
    oldText: string,   // 要替换的精确原文
    newText: string    // 替换文本
  }>,
}
```

- 所有编辑在**原始文件**上一次性匹配（非增量）
- `oldText` 必须在文件中唯一
- 多个编辑不能重叠
- 自动处理 BOM、换行符（CRLF/LF）
- 通过 [`file-mutation-queue.ts`](packages/coding-agent/src/core/tools/file-mutation-queue.ts) 序列化同文件写入

### write — 创建/覆写文件

参数 schema（`write.ts:15-16`）：

```typescript
{
  path: string,        // 目标文件路径
  content: string,     // 文件内容
}
```

- 自动创建父目录
- 通过 [`file-mutation-queue.ts`](packages/coding-agent/src/core/tools/file-mutation-queue.ts) 序列化同文件写入

### grep — 内容搜索

参数 schema（`grep.ts:24-35`）：

```typescript
{
  pattern: string,       // 正则或字面量
  path?: string,         // 搜索目录（默认当前）
  glob?: string,         // 文件名过滤（如 '*.ts'）
  ignoreCase?: boolean,  // 忽略大小写
  literal?: boolean,     // 字面量匹配而非正则
  context?: number,      // 上下文行数
  limit?: number,        // 最大匹配数（默认 100）
}
```

- 底层调用系统 `rg`（ripgrep）
- 长行自动截断

### find — 文件名搜索

参数 schema（`find.ts:22-25`）：

```typescript
{
  pattern: string,     // glob 模式（如 '*.ts', '**/*.spec.ts'）
  path?: string,       // 搜索目录（默认当前）
  limit?: number,      // 最大结果数（默认 1000）
}
```

- 底层调用系统 `fd`
- 自动跳过 `node_modules`、`.git` 等

### ls — 列目录

参数 schema（`ls.ts:14-15`）：

```typescript
{
  path?: string,       // 目录路径（默认当前）
  limit?: number,      // 最大条目数（默认 500）
}
```

- 输出超出限制会截断并显示截断信息

## 可插拔执行层：XxxOperations 架构

### 设计原则：工具定义与 I/O 执行分离

每个工具由两层组成：

| 层 | 职责 | 始终在 agent loop 侧执行 |
|----|------|--------------------------|
| **工具定义层** | 参数 schema、输出截断/格式化、TUI 渲染、错误消息拼装 | 是 |
| **操作执行层** | 最底层的 I/O 原语：读文件、写文件、spawn 进程、搜索文件系统 | 可替换 |

两层通过 `XxxOperations` 接口连接。每个接口都有一套默认的本地实现，也都可以在创建工具时替换为远程实现。这实现了 **agent loop 和工具执行层可以在不同服务上运行**。

### 七把刀的 Operations 接口一览

所有接口都定义在各工具文件中，通过 `packages/coding-agent/src/core/tools/index.ts` 统一导出。

#### read — `ReadOperations`

```typescript
// read.ts:43-51
export interface ReadOperations {
  readFile: (absolutePath: string) => Promise<Buffer>;
  access: (absolutePath: string) => Promise<void>;
  detectImageMimeType?: (absolutePath: string) => Promise<string | null | undefined>;
}
```

默认实现：`fs.readFile` + `fs.access` + MIME 检测。

#### bash — `BashOperations`

```typescript
// bash.ts:39-63
export interface BashOperations {
  exec: (
    command: string,
    cwd: string,
    options: {
      onData: (data: Buffer) => void;  // 流式输出回调
      signal?: AbortSignal;            // 取消信号
      timeout?: number;                // 超时秒数
      env?: NodeJS.ProcessEnv;         // 环境变量
    },
  ) => Promise<{ exitCode: number | null }>;
}
```

`onData` 设计为 `Buffer` 类型而非 `string`，以适应二进制输出流；上层的 ANSI 清洗和二进制过滤由调用方处理。默认实现：`createLocalBashOperations()`，通过 `getShellConfig()` 解析 shell 路径后 `spawn` 子进程并管理生命周期。

#### write — `WriteOperations`

```typescript
// write.ts:25-31
export interface WriteOperations {
  writeFile: (absolutePath: string, content: string) => Promise<void>;
  mkdir: (dir: string) => Promise<void>;
}
```

默认实现：`fs.writeFile` + `fs.mkdir`。

#### edit — `EditOperations`

```typescript
// edit.ts:73-80
export interface EditOperations {
  readFile: (absolutePath: string) => Promise<Buffer>;
  writeFile: (absolutePath: string, content: string) => Promise<void>;
  access: (absolutePath: string) => Promise<void>;
}
```

edit 需要同时读和写（读取原文 → 匹配替换 → 写回），所以接口组合了 read 和 write 的能力。默认实现：`fs.readFile` + `fs.writeFile` + `fs.access`。

#### find — `FindOperations`

`find.ts:41-46`：封装 `fd` 调用，支持 pattern/path/limit。

#### grep — `GrepOperations`

`grep.ts:50-55`：封装 `rg` 调用，支持 pattern/path/glob/ignoreCase/literal/context/limit。

#### ls — `LsOperations`

`ls.ts:31-38`：封装目录读取，支持 path/limit。

### 统一注入点：`ToolsOptions`

`index.ts:90-97` 定义了把所有 Operations 汇聚到一个结构体的选项：

```typescript
export interface ToolsOptions {
  read?: ReadToolOptions;   // { autoResizeImages?, operations?: ReadOperations }
  bash?: BashToolOptions;   // { operations?, commandPrefix?, shellPath?, spawnHook? }
  write?: WriteToolOptions; // { operations?: WriteOperations }
  edit?: EditToolOptions;   // { operations?: EditOperations }
  grep?: GrepToolOptions;
  find?: FindToolOptions;
  ls?: LsToolOptions;
}
```

通过这一个结构体，`createAllTools(cwd, toolsOptions)` 拿到操作系统的全部控制权——从本地文件系统切换到 SSH 远程、Docker 容器、或任何自定义传输层。

bash 还额外提供两个注入维度（均在 `BashToolOptions` 中）：

| 选项 | 作用 | 注入层级 |
|------|------|---------|
| `operations` | 替换 `BashOperations` 实例 | 执行层：把进程 spawn 替换为 SSH/Docker 等 |
| `commandPrefix` | 在每条命令前追加前缀（如 `source ~/.bashrc`） | 命令层：改写命令文本本身 |
| `spawnHook` | 在 `exec` 调用前修改 command/cwd/env | 上下文层：拦截并改写整个执行上下文 |

执行顺序：`commandPrefix 拼接 → spawnHook 拦截 → operations.exec()`

### 分布式架构：agent loop 与工具执行分离

```
┌─────────────────────────────────────────┐
│  Service A（agent loop 所在地）           │
│                                         │
│  LLM 推理 → 决定调哪个工具 → 生成参数    │
│                   │                     │
│                   ▼                     │
│  tool.execute(id, params, signal)       │
│         │                               │
│         ▼                               │
│  myRemoteOps.readFile(path)  ───────────→  Service B（用户机器 / 沙箱）│
│  myRemoteOps.writeFile(...) ────────────→  实际文件系统                 │
│  myRemoteOps.exec(cmd)      ────────────→  实际 bash 进程              │
│                                         │                              │
│  LLM 拿到结果 → 下一轮推理               │                              │
└─────────────────────────────────────────┘
```

关键点：

- 工具调用的**生命周期管理**（参数校验、`OutputAccumulator` 截断、临时文件管理、`fileMutationQueue` 写锁、错误格式化、TUI 渲染）始终在 agent loop 侧执行。
- 只有最底层的 **I/O 原语**被替换。`XxxOperations` 接口都是纯 Promise-based，不绑定任何传输协议—— SSH、HTTP、WebSocket、gRPC、Unix socket 都可以。
- 工具定义层的参数 schema、`renderCall`、`renderResult` 完全复用，不需要为每个远程传输重新实现。

### 三种参考实现模式

代码库的 `packages/coding-agent/examples/extensions/` 中已有三类完整示例：

#### 模式 1：全量远程替换 — `ssh.ts`

替换 read / write / edit / bash 四个工具的 Operations，全部委托给 `ssh user@host <cmd>`。路由路径 `localCwd → remoteCwd`。

关键结构：

```typescript
// 每个 Operations 接口独立实现
createRemoteReadOps(remote, remoteCwd, localCwd): ReadOperations
createRemoteWriteOps(...): WriteOperations
createRemoteEditOps(...): EditOperations   // 组合 read + write
createRemoteBashOps(...): BashOperations

// 通过 registerTool 覆盖内置工具
pi.registerTool({
  ...localRead,              // 复用内置的参数 schema、TUI 渲染
  async execute(...) {
    const tool = createReadTool(cwd, {
      operations: createRemoteReadOps(...)  // 替换执行层
    });
    return tool.execute(...);
  }
});
```

- `ReadOperations.detectImageMimeType` 通过 `file --mime-type` 远端执行
- `WriteOperations.writeFile` 通过 base64 编码 + `base64 -d` 远端写入
- `BashOperations.exec` 通过 `ssh <remote> <cmd>` 远端执行，超时/取消信号转发到 SSH 子进程
- 用户 `!` 命令通过 `user_bash` 事件钩子同样走 SSH
- 系统提示中的 cwd 被替换为远端路径

#### 模式 2：单工具增强 — `sandbox/index.ts`

只替换 `BashOperations`，在命令执行前用 `SandboxManager.wrapWithSandbox(command)` 包装，底层仍是本地 `spawn("bash")`。其他 6 个工具不变。

```typescript
pi.registerTool({
  ...localBash,
  label: "bash (sandboxed)",
  async execute(id, params, signal, onUpdate, _ctx) {
    const sandboxedBash = createBashTool(localCwd, {
      operations: createSandboxedBashOps(),
    });
    return sandboxedBash.execute(id, params, signal, onUpdate);
  },
});
```

#### 模式 3：工具代理/拦截 — `tool-override.ts`

只替换 `read` 的 `execute`，在调用前先检查路径黑名单（`.env`、`secrets`、`.ssh` 等），拦截敏感文件访问；通过的文件才走正常读取。

```typescript
pi.registerTool({
  name: "read",  // 与内置工具同名，会覆盖
  async execute(_toolCallId, params, _signal, _onUpdate, ctx) {
    if (isBlockedPath(absolutePath)) {
      return { content: [{ type: "text", text: "Access denied: ..." }], ... };
    }
    // 通过的文件走本地实现
  },
});
```

这种模式不需要实现 `ReadOperations`——它拦截在工具定义层，而非操作执行层。

### 当前缺的东西

没有内置的"远程工具宿主"抽象。目前不存在类似这样的统一远程传输层：

```typescript
// pi 里不存在这种抽象
interface RemoteWorkspaceProvider {
  connect(url: string): Promise<void>;
  getReadOperations(): ReadOperations;
  getWriteOperations(): WriteOperations;
  getBashOperations(): BashOperations;
  // ...
}
```

开发者需要自己用 `XxxOperations` 接口 + 选定的传输协议（SSH、WebSocket、HTTP 等）拼装远程执行方案。`ssh.ts` 就是官方给出的参考模式——你可以照这个模式实现 Docker exec、K8s pod exec、或自定义 agent 协议。

## 工具的有状态性分析

### 模型视角：无状态

从 LLM 角度看，每个工具调用是 self-contained 的：

```
JSON 参数 → 工具执行 → JSON 结果
```

不需要在两次调用之间维护模型可见的状态。没有 `TodoWrite` 那种跨调用记忆任务列表的工具。

### 实现层面：存在隐式状态

虽然没有显式对模型暴露的状态，但实现中有三种跨调用共享的可变状态：

#### 1. 文件写入锁 — [`file-mutation-queue.ts`](packages/coding-agent/src/core/tools/file-mutation-queue.ts)

```typescript
// 模块级 Map，跨所有工具调用存活
const fileMutationQueues = new Map<string, Promise<void>>();
```

- edit 和 write **共享**这个队列
- 对同一文件连续调用会排队，第二次等第一次完成
- 不同文件并行执行，互不影响

```
edit("foo.ts") → 持锁 → write("foo.ts") → 等锁 → 执行
edit("foo.ts") → 持锁 → edit("bar.ts") → 并行执行（不同文件）
```

**影响**：edit 和 write 对同一文件的操作互相阻塞，第二次调用的执行时机取决于第一次是否完成。失败时会返回 "File is currently being modified" 错误。

#### 2. 后台子进程追踪 — [`shell.ts:172-185`](packages/coding-agent/src/utils/shell.ts#L172)

```typescript
// 模块级 Set，跨所有 bash 调用存活
const trackedDetachedChildPids = new Set<number>();
```

- bash 执行命令时把子进程 PID 注册进去，退出时移除
- 进程异常退出可能残留 PID
- `killTrackedDetachedChildren()` 在会话退出时清理

**影响**：一次 bash 调用的子进程残留可能影响后续调用的进程清理范围。

**注意**：当 `BashOperations` 被替换为远程实现时，这个本地进程追踪机制失效（进程在远端运行）。清理逻辑由远程端自行管理。

#### 3. 文件系统本身

这是最大的"隐式状态"——七个工具共享同一片文件系统：

```
write("a.ts", "hello") → edit("a.ts", ...) → read("a.ts")  // 结果取决于前两步
bash("rm a.ts")        → read("a.ts")                       // 文件已不存在
```

read/grep/find/ls 的结果依赖 edit/write/bash 的历史操作。这不是工具内部状态，而是外部世界的副作用，但对模型来说，反复调用同一工具确实会产生不同结果。

### 总结

| 层面 | 有状态？ | 细节 |
|------|---------|------|
| 模型视角（输入→输出） | 无状态 | 每次调用 self-contained，无跨调用数据依赖 |
| 工具内部（模块级变量） | 有状态 | `fileMutationQueues`（写入锁）、`trackedDetachedChildPids`（子进程追踪） |
| 外部世界（文件系统） | 有状态 | 所有读写操作共享同一 cwd，操作互相影响 |

## 扩展工具

除了 7 个内置工具，扩展系统（[`extensions/types.ts`](packages/coding-agent/src/core/extensions/types.ts)）允许通过 `registerTool()` 注册自定义工具：

```typescript
// 扩展中注册自定义工具
registerTool({
  name: "my-custom-tool",
  description: "Does something useful",
  parameters: Type.Object({ ... }),
  execute: async (id, args, signal, onUpdate) => { ... },
});
```

扩展注册的工具与内置工具混合在同一工具列表中，模型可以同时调用。如果注册的工具名与内置工具相同，会**覆盖**内置工具（如 `ssh.ts` 和 `sandbox/index.ts` 所示）。

## 工具定义结构

每个工具由两部分组成：

1. **`ToolDef`**（工具定义） — `name`、`description`、`parameters`（JSON Schema），发送给 LLM
2. **`Tool`**（工具实例） — `execute(id, args, signal, onUpdate)`，实际执行逻辑

两者由 `createTool()` / `createToolDefinition()` 分别创建，通过 `wrapToolDefinition()` 注入文件操作约束（cwd 沙箱、路径解析等）。

`createXxxToolDefinition()` 返回的 `ToolDef` 还包含 TUI 渲染能力（`renderCall`、`renderResult`），这些在扩展覆盖工具时会被自动继承——只要扩展的 `registerTool()` 不提供自定义渲染函数。
