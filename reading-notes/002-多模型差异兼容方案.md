# 002 - pi-ai 多模型差异兼容方案深度分析

## 核心问题

pi 要支持 OpenAI、Anthropic、Google、Mistral、Azure、Vertex AI、DeepSeek 等数十家 LLM 供应商，它们在以下维度差异巨大：

- **API 协议风格**：OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Google Generative AI、AWS Bedrock Converse — 五套完全不同的事件流和字段命名体系
- **Thinking/推理控制**：`reasoning_effort`（OpenAI） vs `thinking.type/budget`（Anthropic） vs `thinking_config`（Google） vs `enable_thinking`（z.ai） vs `chat_template_kwargs.enable_thinking`（Qwen）
- **Max tokens 字段**：`max_completion_tokens` vs `max_tokens`
- **系统消息角色**：`system` vs `developer`
- **Tool result 格式**：有的需要 `name` 字段，有的不需要；有的不允许 tool result 后直接跟 user 消息
- **Prompt 缓存**：OpenAI `prompt_cache_key` + `prompt_cache_retention` vs Anthropic `cache_control` epemeral markers
- **工具调用 ID 长度**：OpenAI Responses 生成 450+ 字符含特殊符号的 ID，Anthropic 只接受 `[a-zA-Z0-9_-]{1,64}`
- **Thinking 块处理**：有的 API 原生支持 thinking 块，有的需要转为纯文本，有的需要以 `<thinking>` 标签包裹

## 整体架构

```
调用方
  │
  │  stream(model, context) / streamSimple(model, context, options)
  ▼
┌──────────────────────┐
│  stream.ts           │  ← 统一入口：查 api-registry → 分发到对应 provider
│  (stream / complete) │
└──────────────────────┘
  │
  │  model.api 决定走哪个 provider
  ▼
┌──────────────────────┐
│  api-registry.ts     │  ← Map<Api, {stream, streamSimple}>
│  registerApiProvider │     懒加载注册
└──────────────────────┘
  │
  │  按 api 值分发
  ▼
┌──────────────────────────────────────────────────┐
│  各 Provider 实现                                  │
│  openai-completions.ts / anthropic.ts             │
│  google.ts / mistral.ts / openai-responses.ts ... │
└──────────────────────────────────────────────────┘
  │
  │  产生统一的 AssistantMessageEventStream
  ▼
┌──────────────────────┐
│  AssistantMessage    │  ← 统一的返回类型
│  (type-safe, 跨供应商)│
└──────────────────────┘
```

## 五大兼容机制

### 1. API 作为一等公民

每个模型不止属于一个 provider，还绑定一个具体的 **API 协议**：

```typescript
// types.ts
export type KnownApi =
  | "openai-completions"
  | "mistral-conversations"
  | "openai-responses"
  | "azure-openai-responses"
  | "openai-codex-responses"
  | "anthropic-messages"
  | "bedrock-converse-stream"
  | "google-generative-ai"
  | "google-vertex";
```

模型定义中 `api` 字段决定调用哪个 provider 函数：

```typescript
// Model<T> 中：
api: TApi;  // 如 "anthropic-messages"
```

### 2. 两层 API 抽象：stream + streamSimple

每个 provider 导出两个函数：

| 函数 | 目的 | Options 类型 |
|------|------|-------------|
| `stream()` | 全功能，暴露供应商特有选项 | `ProviderSpecificOptions` |
| `streamSimple()` | 统一简化接口 | `SimpleStreamOptions`（reasoning, temperature, maxTokens...） |

```typescript
// openai-completions.ts
export const streamSimpleOpenAICompletions = (model, context, options) => {
  // 将 SimpleStreamOptions 中的 reasoning level
  // 转换为 OpenAI 专有的 reasoningEffort
  const reasoningEffort = options?.reasoning
    ? clampThinkingLevel(model, options.reasoning)
    : undefined;
  // 然后委托给 streamOpenAICompletions
  return streamOpenAICompletions(model, context, {
    ...base,
    reasoningEffort,
  });
};
```

### 3. Compat 自动检测 + 显式覆盖

每个 API 协议有对应的 `Compat` 接口，描述该协议的各种变体差异：

```typescript
// 以 OpenAI Completions 为例 — 17 个兼容开关
export interface OpenAICompletionsCompat {
  supportsStore?: boolean;              // 是否支持 store 字段
  supportsDeveloperRole?: boolean;      // 是否支持 developer 角色
  supportsReasoningEffort?: boolean;    // 是否支持 reasoning_effort
  maxTokensField?: "max_completion_tokens" | "max_tokens";
  requiresToolResultName?: boolean;     // tool result 是否需要 name
  requiresAssistantAfterToolResult?: boolean; // tool result 和 user 之间是否需要 assistant
  requiresThinkingAsText?: boolean;     // thinking 块是否转纯文本
  requiresReasoningContentOnAssistantMessages?: boolean;
  thinkingFormat?: "openai" | "openrouter" | "deepseek" | "together" | "zai" | "qwen" | "qwen-chat-template";
  cacheControlFormat?: "anthropic";     // 是否使用 Anthropic 风格 cache_control
  sendSessionAffinityHeaders?: boolean;
  supportsLongCacheRetention?: boolean;
  // ...
}
```

**自动检测**：`detectCompat(model)` 根据 `model.provider` 和 `model.baseUrl` 推断：

```typescript
function detectCompat(model) {
  const isDeepSeek = provider === "deepseek" || baseUrl.includes("deepseek.com");
  const isZai = provider === "zai" || baseUrl.includes("api.z.ai");
  // ...
  return {
    maxTokensField: useMaxTokens ? "max_tokens" : "max_completion_tokens",
    thinkingFormat: isDeepSeek ? "deepseek" : isZai ? "zai" : /*...*/ "openai",
    supportsReasoningEffort: !isGrok && !isZai && !isMoonshot,
    requiresReasoningContentOnAssistantMessages: isDeepSeek,
    // ...
  };
}
```

**显式覆盖**：模型的 `compat` 字段可以逐个覆盖自动检测的值：

```typescript
function getCompat(model) {
  const detected = detectCompat(model);
  return {
    supportsStore: model.compat?.supportsStore ?? detected.supportsStore,
    maxTokensField: model.compat?.maxTokensField ?? detected.maxTokensField,
    // 每个字段都可以独立覆盖
  };
}
```

### 4. 统一事件流 (Event Stream)

所有 provider 必须输出统一的 `AssistantMessageEventStream`，事件类型完全标准化：

```
start                        ← 流开始
text_start / text_delta / text_end       ← 文本增量
thinking_start / thinking_delta / thinking_end  ← 思考增量
toolcall_start / toolcall_delta / toolcall_end  ← 工具调用增量
done | error                 ← 流终止
```

每个 provider 内部负责将自己的原生流式事件（SSE chunk、gRPC stream 等）映射到这个统一协议。例如：

- **OpenAI Completions**：`chunk.choices[0].delta.content` → `text_delta`
- **Anthropic**：`content_block_delta` (text/tool_use) → `text_delta` / `toolcall_delta`
- **Google**：`candidate.content.parts[]` → 通过 `isThinkingPart(part)` 区分 text 和 thinking

### 5. 跨供应商消息转换 (transformMessages)

会话历史中的 `Message[]` 需要在不同模型间传递时进行转换：

```
Message[] → transformMessages() → Message[] → 各 provider 的 convertMessages()
              │                                  │
              │  通用兼容处理                       │  转成供应商原生格式
              ▼                                  ▼
```

`transformMessages` 做三件事：

1. **图片降级**：非视觉模型的图片转占位文本 `"(image omitted: model does not support images)"`
2. **Thinking 块处理**：跨模型时删除 redacted thinking（加密数据只有原模型能解析）
3. **工具调用 ID 规范化**：OpenAI Responses 的 450+ 字符 ID (`call_xxx|yyy+zzz/aaa=`) 通过回调 `normalizeToolCallId` 规范化为 40 字符以内的 `[a-zA-Z0-9_-]`

每个 provider 还有自己的 `convertMessages` 函数，将统一的 `Message[]` 转成各自的原生格式：

- **OpenAI Completions**：`Message[]` → `ChatCompletionMessageParam[]`（含 system/developer 角色选择、thinking 字段注入、tool_calls 格式化）
- **Anthropic**：`Message[]` → `MessageParam[]`（含 Claude Code stealth mode 工具名匹配、cache_control 注入）
- **Google**：`Message[]` → `Content[]`（含 `thought: true` 标记、thoughtSignature 保留、functionResponse 合并、Gemini 2 vs 3 差异处理）

### 6. Thinking/推理的统一抽象

模型元数据包含 `thinkingLevelMap`，将 pi 的 5 级 thinking（`minimal` / `low` / `medium` / `high` / `xhigh`）映射到各提供商的专有值：

```typescript
// 模型定义中：
thinkingLevelMap: {
  minimal: "minimal",    // OpenAI: reasoning_effort 用此值
  low: "low",
  medium: "medium",
  high: "high",
  // xhigh 映射为 null 表示不支持
}
```

不同提供商的 thinking 控制方式：

| 提供商 | 参数方式 |
|--------|---------|
| OpenAI | `reasoning_effort: "medium"` |
| Anthropic 自适应模型 | `thinking.type: "adaptive"`, `output_config.effort: "medium"` |
| Anthropic 旧模型 | `thinking.type: "enabled"`, `thinking.budget_tokens: 8192` |
| DeepSeek | `thinking: { type: "enabled" }` + `reasoning_effort` |
| OpenRouter | `reasoning: { effort: "medium" }` |
| z.ai | `enable_thinking: true` |
| Together | `reasoning: { enabled: true }` + `reasoning_effort` |
| Google | `thinkingConfig: { thinkingLevel: "MEDIUM" }` |

`streamSimple()` 通过 `thinkingFormat` compat 字段决定使用哪种参数格式。

### 7. Prompt 缓存兼容

不同提供商的 prompt 缓存机制完全不同：

| 提供商 | 机制 |
|--------|------|
| OpenAI | `prompt_cache_key` + `prompt_cache_retention` 顶层参数 |
| Anthropic | 在消息内容的特定位置注入 `cache_control: { type: "ephemeral" }` marker |
| OpenAI Compat（Anthropic 缓存风格） | compat 设为 `cacheControlFormat: "anthropic"`，在 system prompt 最后一段、最后一个 tool、最后一条 user/assistant 消息上附加 `cache_control` marker |

### 8. 懒加载注册

所有 provider 模块通过 `register-builtins.ts` 懒加载注册，避免启动时加载所有 SDK：

```typescript
// 首次调用时才 import provider 模块
function loadOpenAICompletionsProviderModule() {
  openAICompletionsProviderModulePromise ||= import("./openai-completions.ts")
    .then(module => ({ stream: module.streamOpenAICompletions, ... }));
  return openAICompletionsProviderModulePromise;
}
```

这允许 pi 在运行时只加载实际使用的 provider 代码。

## 总结：兼容策略全景

```
                    ┌── 自动检测（detectCompat）
         ┌── Compat ──┤
         │          └── 显式覆盖（model.compat）
         │
         ├── 两层 API（stream + streamSimple）
         │
         ├── 统一事件流（AssistantMessageEventStream）
         │
pi-ai ───┼── 消息转换管道
         │     ├── transformMessages（通用兼容）
         │     └── convertMessages（供应商原生格式）
         │
         ├── Thinking 统一抽象（thinkingLevelMap + thinkingFormat）
         │
         ├── 缓存兼容（cacheControlFormat compat 开关）
         │
         └── 懒加载注册（按需 import provider 模块）
```

核心思想：**将差异建模为类型 + 配置，而非 if-else**。每个差异维度（API 协议、reasoning 格式、缓存方式）都有对应的类型字段和 compat 开关，自动检测提供合理默认值，显式覆盖处理边缘情况，provider 实现代码只关注自己协议的细节。
