# 009 - 会话持久化"表结构"

## 一句话定位

Pi **没有数据库、没有 SQL**。持久化用的是 **append-only 的 JSONL 文件**，每个会话一个 `.jsonl`，**每行一条记录**，整体是一棵 **event-sourcing 风格的会话树**。所谓"表结构"，就是这些行记录（`SessionTreeEntry`）的 schema。

核心目录：`packages/agent/src/harness/session/`

| 文件 | 职责 |
|------|------|
| `jsonl-storage.ts` | JSONL 文件读写、解析、append（落盘实现） |
| `jsonl-repo.ts` | 会话仓库：create/open/list/delete/fork、路径编码 |
| `session.ts` | `Session` 高层 API + `buildSessionContext`（把树重建成消息） |
| `memory-storage.ts` / `memory-repo.ts` | 纯内存实现（测试 / 临时会话，非落盘） |
| `repo-utils.ts` | ID、时间戳、fork 取分支 |
| `uuid.ts` | 自实现 UUIDv7（时间有序） |
| `../types.ts` | 所有 entry 类型定义（line 334-447） |

## 二、文件格式：第 1 行是表头，其余每行一条 entry

### 表头行（SessionHeader，`jsonl-storage.ts:8`）

| 字段 | 类型 | 说明 |
|------|------|------|
| `type` | `"session"` | 固定 |
| `version` | `3` | **schema 版本，必须是 3**，否则报 `unsupported session version` |
| `id` | string | 会话 id（uuidv7） |
| `timestamp` | ISO string | 创建时间 |
| `cwd` | string | 会话工作目录 |
| `parentSession` | string? | 父会话文件路径（fork 时记录来源） |

解析严格：第一行必须能解析成合法 header，否则整文件视为 `invalid_session`（`list` 时会跳过这类坏文件，`parseHeaderLine`）。

### 记录行（SessionTreeEntry）

所有 entry 共享基类（`types.ts:334`）：

| 公共字段 | 类型 | 说明 |
|------|------|------|
| `type` | string | 判别式（discriminator） |
| `id` | string | entry id，**uuidv7 前 8 位**，文件内唯一 |
| `parentId` | string \| null | 父 entry id；null 表示根 |
| `timestamp` | ISO string | 写入时间 |

## 三、"表"清单：10 种 entry 类型

`SessionTreeEntry` 是一个判别联合（`types.ts:404`）。把每种 type 当成一张"表"：

| type | 专有字段 | 作用 |
|------|----------|------|
| `message` | `message: AgentMessage` | **主体**：一条 user/assistant/tool 消息（含 provider/model） |
| `thinking_level_change` | `thinkingLevel: string` | 切换思考档位 |
| `model_change` | `provider`, `modelId` | 切换模型 |
| `compaction` | `summary`, `firstKeptEntryId`, `tokensBefore`, `details?`, `fromHook?` | 上下文压缩点：摘要 + 从哪条起保留原文 |
| `branch_summary` | `fromId`, `summary`, `details?`, `fromHook?` | 跳转分支时对旧分支的摘要 |
| `custom` | `customType`, `data?` | 扩展自定义数据（不进消息流） |
| `custom_message` | `customType`, `content`, `display`, `details?` | 自定义消息（可进消息流，`display` 控制是否展示） |
| `label` | `targetId`, `label?` | 给某条 entry 打/清标签（label 为空即删除） |
| `session_info` | `name?` | 会话命名（`type` 是 legacy 名，保留兼容） |
| `leaf` | `targetId: string \| null` | **指针记录**：把"当前活跃叶子"移动到 targetId |

> 关键点：**所有变更都是 append**——改模型、改思考档、命名、压缩、打标签，统统是追加一行新 entry，**从不原地修改历史**。这就是 event sourcing：当前状态由"重放全部 entry"推导出来。

---

## 四、树模型与"当前叶子"

### parentId 构成树
每条 entry 用 `parentId` 指向上一条，形成链/树。`getPathToRoot(leafId)`（`jsonl-storage.ts:275`）从叶子沿 parentId 一路回溯到根，得到一条**分支路径**——这才是要喂给模型的上下文。

### leaf entry = 可持久化的"HEAD 指针"
活跃叶子不是靠"最后一行"隐式决定，而是显式记录：
- 普通 entry 写入后，叶子 = 该 entry 的 `id`（`leafIdAfterEntry`）。
- `leaf` 类型 entry 写入后，叶子 = 它的 `targetId`（可为任意历史 entry，甚至 null=回到空）。
- `setLeafId()`（`jsonl-storage.ts:226`）就是 append 一条 leaf entry 来"移动 HEAD"。

这让**分支跳转本身也被持久化、可追溯**，类似 git 的 reflog。

### 分支与 fork
- **同文件内分支**：`moveTo(entryId, summary?)` 把叶子移到某历史 entry，之后的 append 就长出新分支；可选地写一条 `branch_summary` 记录对旧分支的总结（`session.ts:232`）。
- **跨文件 fork**：`JsonlSessionRepo.fork`（`jsonl-repo.ts:133`）新建一个 `.jsonl`，header 的 `parentSession` 指向源文件，把源分支的 entry 复制进去。
  - `getEntriesToFork`（`repo-utils.ts:32`）：`position:"at"` 从目标 entry 起；默认 `"before"` 要求目标是 **user 消息**，从其 parent 起（即"在这条用户消息之前重开"）。

## 五、重建上下文：buildSessionContext

`buildSessionContext(pathEntries)`（`session.ts:21`）把一条分支路径还原成 `SessionContext { messages, thinkingLevel, model }`：

1. 顺序扫描，遇到 `thinking_level_change` / `model_change` / assistant message 更新当前档位与模型；遇到 `compaction` 记下压缩点。
2. 生成 messages：
   - `message` → 直接取出
   - `custom_message` → 重建为自定义消息
   - `branch_summary` → 重建为分支摘要消息
3. **压缩处理**：若存在 compaction，则先放一条压缩摘要消息，再**只保留从 `firstKeptEntryId` 起、以及压缩点之后**的 entry。压缩前更早的原文被摘要替代，省 token。

> 即：**磁盘存全量历史（含被压缩的原文），喂给模型时按 compaction 规则裁剪**。历史不丢，上下文可控。

## 六、存储抽象与可替换后端

`SessionStorage<TMetadata>` 接口（`types.ts:433`）定义了 getLeafId/setLeafId/appendEntry/getEntry/findEntries/getLabel/getPathToRoot/getEntries 等。两套实现：

| 实现 | 落盘 | 用途 |
|------|------|------|
| `JsonlSessionStorage` | ✅ JSONL 文件 | 生产 |
| `InMemorySessionStorage` | ❌ 仅内存 | 测试 / 临时会话 |

两者逻辑几乎一致（树回溯、label 缓存、leaf 指针），只差 append 是否 `fs.appendFile`。`SessionRepo` 同理有 `JsonlSessionRepo` / `InMemorySessionRepo`。**这层抽象让"持久化方式"可插拔**——理论上换 DB 后端只需实现接口。

### 内存索引
打开文件时（`loadJsonlStorage`）一次性读入全部行，构建：
- `entries[]` 顺序数组
- `byId: Map` 快速按 id 查
- `labelsById: Map`（重放 label entry 得到的当前标签）
- `currentLeafId`

之后读操作全在内存，写操作既 append 落盘又更新内存索引（`appendEntry`，`jsonl-storage.ts:250`）。

## 七、ID 方案：UUIDv7 + 截断

`uuid.ts` 自实现 **UUIDv7**（前 48 位是毫秒时间戳 → **时间有序**，利于按生成顺序排序、做文件名前缀）。
- 会话 id 用完整 uuidv7。
- entry id 用 **前 8 个 hex 字符**（`generateEntryId`），冲突则重试 100 次，再不行退回完整 uuid。文件内小规模下 8 位足够且更短。

## 设计要点回顾

1. **Append-only JSONL**：一行一记录，崩溃安全、易 diff、易回放、无需 DB。
2. **Event sourcing**：状态（模型/档位/标签/叶子）由重放 entry 推导，历史不可变。
3. **持久化的树 + leaf 指针**：分支跳转、fork、压缩都被记录，可追溯（类 git）。
4. **存全量、喂裁剪**：compaction 在读取时裁剪上下文，磁盘仍留原文。
5. **存储接口可插拔**：JSONL 与内存两实现共享同一接口。

## 九、若改用 MySQL 做持久层，表结构怎么设计

> 思路：**别试图把 JSONL 拍平成传统业务表**。pi 的本质是 *append-only 事件溯源 + 会话树*，MySQL 设计要**保住这四个特性**：① 只追加不改历史；② `parent_id` 自引用成树；③ leaf 指针（HEAD）；④ 存全量、读取时重放推导状态。靠 `SessionStorage` 接口可插拔（见第六章），换 MySQL 后端只需实现该接口，应用层 `buildSessionContext` 逻辑不动。

### 9.1 两种建模取向

| 方案 | 形态 | 取舍 |
|------|------|------|
| **A. 单表 + JSON（推荐）** | 一张 `session_entries`，类型专有字段塞 `JSON payload` | 最贴近 JSONL、追加快、schema 灵活、几乎不用 join；代价是部分字段查询要走 JSON/生成列 |
| B. 按类型拆表 | `session_entries` 基表 + `entry_message`/`entry_compaction`… 子表 | 更"关系化"、强类型约束；代价是 10 种类型 10 张表、读分支要多表 join、加新类型要改 DDL |

事件溯源场景下 entry 是**异构、只追加、很少按内部字段做复杂查询**的——**方案 A 更合适**。下面按方案 A 给出。

### 9.2 `sessions` 表（对应 JSONL 表头）

```sql
CREATE TABLE sessions (
  id                CHAR(36)      NOT NULL,            -- 会话 id（uuidv7）
  version           SMALLINT      NOT NULL DEFAULT 3,  -- schema 版本
  created_at        DATETIME(3)   NOT NULL,            -- 毫秒精度，对齐 ISO 时间戳
  cwd               VARCHAR(1024) NOT NULL,            -- 工作目录
  cwd_hash          BINARY(32)    NOT NULL,            -- SHA-256(cwd)，给等值查询建索引用
  parent_session_id CHAR(36)      NULL,                -- fork 来源（原 header.parentSession）
  -- 下面两列是物化派生值，免去每次重放：
  name              VARCHAR(255)  NULL,                -- 最新 session_info.name
  leaf_entry_id     CHAR(8)       NULL,                -- 当前 HEAD（活跃叶子）
  PRIMARY KEY (id),
  KEY idx_sessions_cwd   (cwd_hash),                   -- list({cwd}) 按目录筛
  KEY idx_sessions_time  (created_at),                 -- 列表按时间排序
  CONSTRAINT fk_sessions_parent FOREIGN KEY (parent_session_id)
    REFERENCES sessions(id) ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- `cwd` 太长不能整列建索引，所以加 `cwd_hash` 做等值查找（原实现的 `encodeCwd` 目录分桶在这里退化为按 hash 索引）。
- `name` / `leaf_entry_id` 是**物化的派生状态**：原 JSONL 靠重放 `session_info`/`leaf` entry 得到，这里在写入时顺手更新一列，读取 O(1)。

### 9.3 `session_entries` 表（核心：会话树）

```sql
CREATE TABLE session_entries (
  seq         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,  -- 全局追加序号 = JSONL 行序
  session_id  CHAR(36) NOT NULL,
  entry_id    CHAR(8)  NOT NULL,                        -- uuidv7 前 8 位，会话内唯一
  parent_id   CHAR(8)  NULL,                            -- 树父节点（同会话内）；NULL=根
  type        ENUM('message','thinking_level_change','model_change',
                   'compaction','branch_summary','custom','custom_message',
                   'label','session_info','leaf') NOT NULL,
  created_at  DATETIME(3) NOT NULL,                     -- entry.timestamp
  payload     JSON NOT NULL,                            -- 类型专有字段（见 9.4）
  -- 高频查询字段用生成列抽出来建索引，存储仍在 payload 里：
  target_id   CHAR(8) AS (payload->>'$.targetId') VIRTUAL,  -- label / leaf 用
  PRIMARY KEY (seq),                                    -- 聚簇按追加顺序，顺序扫描重放最快
  UNIQUE KEY uq_entry  (session_id, entry_id),          -- entry_id 必须配 session_id 才唯一
  KEY idx_parent       (session_id, parent_id),         -- 回溯树
  KEY idx_type         (session_id, type),              -- findEntries(type)
  KEY idx_target       (session_id, target_id),
  CONSTRAINT fk_entries_session FOREIGN KEY (session_id)
    REFERENCES sessions(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

设计要点：
- **`seq`（AUTO_INCREMENT）作主键**：等价于"JSONL 行号"，给出**全局追加顺序**——重放、计算叶子、按时间排序都靠它。InnoDB 聚簇索引让物理存储就是追加顺序，顺序扫描分支极快。
- **`entry_id` 8 位、仅会话内唯一**：原实现就是 `uuidv7().slice(0,8)`，跨会话会复用，所以**所有引用必须带 `session_id`**，用 `UNIQUE(session_id, entry_id)` 兜底，碰撞时插入失败→应用层重试（对齐 `generateEntryId` 的重试逻辑）。
- **`payload JSON` 装异构字段**，大文本（message 内容）放 JSON 即可（InnoDB JSON 底层是 LONGBLOB，够大）。需要索引的字段（如 `targetId`）用**生成列 VIRTUAL** 抽出再建二级索引，不额外占行内空间。

### 9.4 `payload` 里各类型存什么（对应第三章 10 种表）

| type | payload 关键字段 |
|------|------------------|
| `message` | `{ message: {...AgentMessage, role, provider, model} }` |
| `model_change` | `{ provider, modelId }` |
| `thinking_level_change` | `{ thinkingLevel }` |
| `compaction` | `{ summary, firstKeptEntryId, tokensBefore, details?, fromHook? }` |
| `branch_summary` | `{ fromId, summary, details?, fromHook? }` |
| `custom` | `{ customType, data? }` |
| `custom_message` | `{ customType, content, display, details? }` |
| `label` | `{ targetId, label? }` |
| `session_info` | `{ name? }` |
| `leaf` | `{ targetId }` |

### 9.5 派生状态：物化 vs 重放

原实现打开文件时一次性重放出 `byId` / `labelsById` / `currentLeafId`。MySQL 下两种做法：

- **leaf / name**：写入时同事务更新 `sessions.leaf_entry_id` / `sessions.name`（物化），读取 O(1)。
- **labels**：可建一张物化表，避免每次重放：

```sql
CREATE TABLE session_labels (
  session_id CHAR(36) NOT NULL,
  target_id  CHAR(8)  NOT NULL,            -- 被打标签的 entry
  label      VARCHAR(255) NOT NULL,
  PRIMARY KEY (session_id, target_id),
  CONSTRAINT fk_labels_session FOREIGN KEY (session_id)
    REFERENCES sessions(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```
写 `label` entry 时：`label` 非空→UPSERT，空→DELETE（对齐 `updateLabelCache`）。

> 仍保留 `leaf` / `label` / `session_info` 作为 `session_entries` 里的真实行——**历史不可变**，物化表只是它们的"当前快照"。

### 9.6 关键操作怎么落到 SQL

**追加 entry（一个事务，保证原子）**
```sql
START TRANSACTION;
INSERT INTO session_entries (session_id, entry_id, parent_id, type, created_at, payload)
VALUES (?, ?, ?, ?, ?, ?);
-- 普通 entry：叶子=自身；leaf entry：叶子=payload.targetId
UPDATE sessions SET leaf_entry_id = ? WHERE id = ?;
-- 若 type=label → UPSERT/DELETE session_labels；若 type=session_info → UPDATE sessions.name
COMMIT;
```

**取分支 getPathToRoot（MySQL 8.0 递归 CTE）**
```sql
WITH RECURSIVE branch AS (
  SELECT * FROM session_entries
   WHERE session_id = :sid AND entry_id = :leaf            -- 从叶子起
  UNION ALL
  SELECT e.* FROM session_entries e
    JOIN branch b
      ON e.session_id = b.session_id AND e.entry_id = b.parent_id
)
SELECT * FROM branch ORDER BY seq;                          -- seq 升序 = 根→叶
```
拿到分支后，`buildSessionContext` 的重放/压缩裁剪逻辑**仍在应用层**，SQL 只负责取出这条链。

**列出会话**：`SELECT ... FROM sessions WHERE cwd_hash=? ORDER BY created_at DESC;`
**按类型找**：`SELECT ... FROM session_entries WHERE session_id=? AND type=? ORDER BY seq;`
**fork**：在 `sessions` 插新行（`parent_session_id` 指源会话），把源分支 entry 批量 `INSERT ... SELECT` 进新 `session_id`（`getEntriesToFork` 选好范围）。

### 9.7 从 JSONL 迁移

逐文件：第 1 行 header → `INSERT sessions`；其余每行按**原顺序**流式 `INSERT session_entries`（`seq` 自增天然保序）；迁移完跑一遍重放，回填 `sessions.leaf_entry_id` / `name` 与 `session_labels`。

### 9.8 取舍提醒

- **失去的**：JSONL 的"零依赖、崩溃只丢最后一行、git 友好"。换来并发、事务、跨会话查询、聚合分析能力。
- **别过度规范化**：把 message 内容拆成多表得不偿失——异构事件用 JSON 列最省心。
- **并发写**：单会话天然串行（append-only + 叶子单调），多会话并行无冲突；`UNIQUE(session_id, entry_id)` + 重试处理 id 碰撞。
- **字符集**：统一 `utf8mb4`，承载多语言 message 内容。
