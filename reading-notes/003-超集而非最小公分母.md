# 003 - 统一抽象的真相：不是最小公分母，是所有供应商字段的超集

## 你的直觉是对的

你问：

> "那你的 response 里面，也要包括所有 api 的全部字段。这个 response，就不是一个自定义的统一抽象，更像是所有 api response 的集合体"

**完全正确。** `AssistantMessage` 不是干净的最小公共抽象，而是所有供应商专有字段的**超集/并集**。

## 证据：AssistantMessage 的字段清单

```typescript
// packages/ai/src/types.ts
export interface AssistantMessage {
  role: "assistant";
  content: (TextContent | ThinkingContent | ToolCall)[];  // ← 看似统一
  api: Api;          // ← 记录来源 API 协议
  provider: Provider; // ← 记录来源供应商
  model: string;      // ← 记录来源模型 ID
  usage: Usage;
  stopReason: StopReason;
  errorMessage?: string;
  timestamp: number;
  responseId?: string;     // ← 供应商专有响应 ID
  responseModel?: string;  // ← 供应商路由后的实际模型名
}
```

三个内容块也各自携带供应商专有数据：

```typescript
export interface ThinkingContent {
  type: "thinking";
  thinking: string;
  thinkingSignature?: string;   // ← Anthropic 加密 thinking 的 opaque data
  redacted?: boolean;           // ← Anthropic redacted_thinking 标记
}

export interface TextContent {
  type: "text";
  text: string;
  textSignature?: string;       // ← OpenAI Responses 的 text signature (JSON v1)
}

export interface ToolCall {
  type: "toolCall";
  id: string;
  name: string;
  arguments: Record<string, any>;
  thoughtSignature?: string;    // ← Google 的 thought signature
}
```

**每一个字段都泄漏了特定供应商的协议细节。**

## 数据生命周期：全链路追踪

### 1. 生成阶段：供应商 → 统一类型（满载）

以 Anthropic 为例（`packages/ai/src/providers/anthropic.ts`）：

```typescript
// content_block_start: "redacted_thinking" → 把加密数据存入 thinkingSignature
} else if (event.content_block.type === "redacted_thinking") {
  const block = {
    type: "thinking",
    thinking: "[Reasoning redacted]",
    thinkingSignature: event.content_block.data,  // ← 加密 opaque payload
    redacted: true,
  };
  output.content.push(block);
}

// signature_delta → 累积签名
} else if (event.delta.type === "signature_delta") {
  block.thinkingSignature += event.delta.signature;
}
```

同理，Google 的 `thoughtSignature`（`google-shared.ts`）：

```typescript
// 保留 thoughtSignature 用于上下文回放
export function retainThoughtSignature(existing, incoming) {
  if (typeof incoming === "string" && incoming.length > 0) return incoming;
  return existing;
}
```

### 2. 持久化阶段：完整保存

会话管理（`agent/src/harness/session/session.ts`）只是把 `AgentMessage[]` 序列化存储。它**不知道也不关心** `thinkingSignature` / `thoughtSignature` 是什么 — 只是完整保存。

```typescript
// Session 只关心 AgentMessage 结构，不碰 content 内部字段
async appendMessage(message: AgentMessage): Promise<string> {
  return this.appendTypedEntry({
    type: "message", message,  // ← 原样存储，包括所有签名
  });
}
```

### 3. 回放阶段（同模型）：完整还原

当 **同一模型** 被再次调用时，`transformMessages` 检测到 `isSameModel === true`，所有专有字段**原样保留**：

```typescript
// transform-messages.ts
const isSameModel =
  assistantMsg.provider === model.provider &&
  assistantMsg.api === model.api &&
  assistantMsg.model === model.id;

if (block.type === "thinking") {
  if (block.redacted) {
    return isSameModel ? block : [];  // ← 同模型：保留加密数据
  }
  if (isSameModel && block.thinkingSignature) return block;  // ← 同模型：保留签名
}
```

然后 Anthropic 的 `convertMessages` 把签名**还原成 Anthropic 原生格式**：

```typescript
// anthropic.ts convertMessages()
if (block.type === "thinking") {
  if (block.redacted) {
    blocks.push({
      type: "redacted_thinking",   // ← 还原为 Anthropic 原生类型！
      data: block.thinkingSignature!,
    });
  } else if (block.thinkingSignature) {
    blocks.push({
      type: "thinking",
      thinking: block.thinking,
      signature: block.thinkingSignature,  // ← 签名带回 API
    });
  }
}
```

### 4. 跨模型切换：选择性裁剪

当切换到**不同模型**时，`transformMessages` 裁剪掉无法跨供应商传递的字段：

```typescript
// Redacted thinking → 直接丢弃（加密数据只有原模型能解析）
if (block.redacted) return isSameModel ? block : [];

// 有签名的 thinking → 转纯文本（去掉签名）
if (!block.thinking || block.thinking.trim() === "") return [];
if (isSameModel) return block;
return { type: "text", text: block.thinking };  // ← 降级为纯文本

// toolCall 的 thoughtSignature → 剥离
if (!isSameModel && toolCall.thoughtSignature) {
  normalizedToolCall = { ...toolCall };
  delete normalizedToolCall.thoughtSignature;
}

// text 的 textSignature → 剥离
if (isSameModel) return block;
return { type: "text", text: block.text };  // ← 不带签名
```

## 这就是"超集"模式

```
                    ┌─────────────────────────────────┐
                    │      AssistantMessage（超集）      │
                    │                                  │
                    │  ┌─ thinking (通用)               │
                    │  │  ├─ thinkingSignature (Anth)  │
                    │  │  └─ redacted (Anth)           │
                    │  ├─ text (通用)                   │
                    │  │  └─ textSignature (OpenAI)    │
                    │  ├─ toolCall (通用)               │
                    │  │  └─ thoughtSignature (Google) │
                    │  ├─ responseId (通用可选)          │
                    │  └─ responseModel (通用可选)       │
                    └─────────────────────────────────┘
                     ↑                ↑
            同模型回放：全部保留    跨模型：裁剪供应商专有字段
```

## 这意味着什么

1. **"统一抽象"不是 clean abstraction** — 它不隐藏供应商差异，而是把差异**编码为可选字段**

2. **`streamSimple` 仍然有效** — 它统一的是**调用方关心的参数**（temperature、maxTokens、reasoning level），而不是 response 结构。response 永远是满载的超集

3. **跨模型切换有信息损失** — redacted thinking 直接丢失，thinking 带签名 → 纯文本降级，Google thought signatures 被剥离。这些是不可避免的，因为不同 API 的协议从根本上不兼容

4. **Agent loop 是传递者，不是仲裁者** — agent harness 不解析、不修改 provider-specific 字段。它只是把 `AssistantMessage[]` 原样传给 LLM provider。provider 层的 `transformMessages` + `convertMessages` 才是真正理解并处理这些差异的地方

5. **设计取舍：宁愿多存，不愿少存** — 保存所有供应商字段的超集，比每个供应商维护一套独立的消息类型要简单。代价是类型定义"臃肿"（8 个供应商专有字段），但收益是 agent loop 完全不需要感知供应商差异
